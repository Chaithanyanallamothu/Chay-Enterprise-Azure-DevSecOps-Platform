# 11 - HPA Autoscaling Validation

**Author:** Chaithanya Nallamothu
**Role:** Senior DevSecOps Engineer

## Objective

The autoscaling checkpoint validates that the application can scale horizontally in response to CPU utilization generated by a controlled in-cluster k6 workload.

## HPA Configuration

The HPA is defined through Helm.

Final configuration:

    minimum replicas: 1
    maximum replicas: 3
    CPU target:       30%

The maximum is deliberately small because this project runs on a shared resource-constrained AKS environment.

## Scale Behavior

The HPA configuration includes controlled scale-up and scale-down behavior.

The objective is to demonstrate observable scaling without creating unnecessary replica churn or excessive resource consumption.

## Load Scenario

Autoscaling test:

    load-tests/autoscaling.js

Configuration:

    40 virtual users
    3 minute duration

The workload repeatedly sends:

    POST /api/orders

This creates sustained application CPU pressure.

## Initial 50% Target

The first HPA target was:

    50%

During the initial autoscaling validation, sustained application CPU utilization remained around:

    40%

Kubernetes correctly did not scale the application because utilization remained below the configured target.

This was not an HPA malfunction.

It showed that the HPA was respecting its configured threshold.

## Final 30% Target

For the controlled autoscaling demonstration, the CPU target was changed to:

    30%

With the same load pattern, CPU utilization exceeded the target and the HPA produced deterministic scale-out.

## Successful Scale-Out

The successful run observed:

    1 replica
       |
       v
    2 replicas
       |
       v
    3 replicas

The application reached the configured maximum of three replicas.

The validation pipeline observed HPA state repeatedly during the k6 execution rather than checking only the final replica count.

## Metrics Server

The runtime validation confirmed the metrics path required by HPA.

The pipeline was able to observe CPU utilization and HPA state.

## Temporary Authorization

Introducing the HPA resource required a controlled Argo CD authorization change.

Temporary elevated AKS access was used for the required bootstrap operation.

After the configuration was applied, the elevated role was revoked.

The normal private-agent access returned to the Reader-oriented model.

## Why the Target Is Environment Specific

The 30% target exists to make scale-out deterministic within this small validation environment.

It is not presented as a production recommendation.

A production HPA target would be based on real workload behavior, resource sizing, SLOs, scaling latency, and capacity testing.
